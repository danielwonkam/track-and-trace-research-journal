    Reconstructed project history¶

    This history was reconstructed from Git commits, dated data-session directories, experiment metadata, current code, and written project records. Dates marked recorded are supported directly by those artifacts. Where an exact date is not available, the text avoids inventing one.

    2026-07-13 — Initial repository and thesis architecture¶

    Evidence level: recorded by Git commit 46fdb38.

    The project established its repository structure, quality criteria, Python package, tests, dashboard area, documentation folders, and a layered target architecture: capture, detection, tracking, zone mapping, interpretation, storage, evaluation, and dashboard. The safety boundary was observation only; the AI was not to control the shopfloor.

    The initial plan mentioned Streamlit, YOLO, ByteTrack/BoT-SORT, and SQLite. These were planning choices rather than final implementation facts.

    2026-07-20 — First hybrid tracking prototype¶

    Evidence level: recorded by Git commit 3e47e72 and experiment folders.

    A rapid hybrid method was added for the FTS and red and white workpieces. The FTS prototype combined YOLOE visual-prompt detection with CSRT tracking. This choice made it possible to test an object-specific detector without first labelling and training a dataset. Classical colour/motion methods supported workpiece exploration on the CPU-only development machine.

    This stage demonstrated feasibility but did not yet provide a fixed experiment configuration or held-out accuracy measurement.

    2026-07-21 — Live camera pipeline and latency investigation¶

    Evidence level: recorded by dated live-session directories and current live modules/tests.

    Camera smoke tests progressed to live shopfloor sessions. The main engineering problem was temporal latency: processing queued frames or moving preview images through disk made the displayed view stale. The pipeline moved toward a dedicated capture loop, latest-frame-only buffering, and separation of preview publication from slower inference. Dynamic camera discovery was introduced so connected cameras could be selected rather than assumed by a hard-coded index.

    2026-07-22 — Repeated shopfloor validation¶

    Evidence level: recorded by multiple dated live-session directories.

    The live pipeline was exercised repeatedly under shopfloor conditions. These sessions provided engineering evidence for camera handling and runtime behaviour, but they were not labelled accuracy experiments. They should therefore not be used to claim detector precision or tracking accuracy.

    2026-07-21 to 2026-07-27 — Dashboard architecture changed¶

    Evidence level: recorded by current implementation, tests, README, and the legacy-plan warning in the backlog; exact change date is bounded but not committed separately.

    The planned Streamlit dashboard was replaced by FastAPI and plain HTML/CSS/JavaScript. WebSocket carries live state and events, MJPEG carries the annotated image stream, and REST endpoints control sessions, camera discovery, replay, deletion, and review. This architecture was selected because direct streaming and independently updating channels fit real-time behaviour better than full-script reruns.

    Session replay retained a compact dropdown, and individual recorded sessions could be deleted through explicit red delete controls with protected path handling.

    2026-07-27 — Formal FTS baseline¶

    Evidence level: recorded by commit 747d198, baseline configuration, metrics, and summary.

    A sequential FTS roadmap was introduced to prevent further ad hoc tuning. The unchanged YOLOE + CSRT method was run on all six 1920×1080, 30 FPS recordings: two red, two blue, and two white sessions. The baseline fixed the reference, stride, redetection interval, confidence setting, image size, CPU device, zone map, and spatial constraints.

    The automated result reported 99.8–100.0% output coverage and four suspicious jumps. Five uninterrupted runs processed approximately 14–23 source FPS. The od_blue_2 runtime was rejected as a performance benchmark because computer sleep contaminated wall-clock time.

    The key methodological limitation was recognised: output continuity showed only that some box was emitted, not that the box represented the FTS.

    2026-07-27 to 2026-07-28 — Human-review workflow¶

    Evidence level: recorded by dashboard code, review log, report, and tests.

    A dedicated FTS review workspace was added to the FastAPI dashboard. It presented every periodic detector lock, suspicious jump, and no-output gap, allowed nearby frame inspection, and stored structured decisions in an append-only JSONL log. Saving a newer row corrected a verdict without deleting history.

    A reproducible summary generator was added to reconstruct the expected queue, select the latest decision per candidate, verify completeness, and produce JSON and Markdown reports.

    2026-07-28 — Baseline review completed¶

    Evidence level: recorded by 130 final candidate decisions and generated reports.

    All 130 candidates were reviewed. Only 37 of 123 periodic detector locks were correct, corresponding to 30.1% checkpoint correctness. Eighty-two candidates were classified as station false locks. Both blue sessions and od_white_1 had zero correct periodic detector locks.

    The result disproved the assumption that near-complete output coverage meant reliable tracking. It also showed that confidence thresholding was not a useful single fix: station false locks had a higher mean confidence than correct locks. The single-reference configuration was therefore rejected for unchanged live transfer.

    Repeated navigation had produced 304 append-only rows for 130 unique candidates. The history was preserved, latest-decision semantics were tested, and the UI was changed to disable an unchanged save.

    2026-07-28 — Supervisor scope decision and scientific journal¶

    Evidence level: supervisor meeting record and documentation files.

    The supervisor requested continuous documentation of activities, mistakes, solutions, and scientifically justified method choices. The technical scope was narrowed to completing FTS detection and tracking before other tracked objects or detailed statistics.

    The next active milestone is a verified one-class fts ground-truth dataset. It must contain positive and negative station-only frames from all six videos, use video/segment-separated splits, and be manually checked before detector training or comparison begins.

    2026-08-04 — Frozen tracker selection and six-route Replay¶

    Evidence level: recorded by commit 4e745d7, locked evaluation artifacts, the six published Replay trajectories, and the 2026-08-04 journal.

    The locked validation-first comparison selected YOLO11n + CSRT over YOLO11n + ByteTrack for the present one-object FTS task. On the locked temporal test, CSRT recorded 144 TP, 0 FP, and 0 FN at the sampled truth points, while ByteTrack recorded 88 TP, 0 FP, and 56 FN. The conclusion is limited to the fixed dataset and protocol.

    All six native route videos were published to the FastAPI Replay interface. Native MP4 playback, compact synchronized overlays, FTS-only station events, journey state, and Live transfer were implemented. Physical Live route validation remained pending because the operator was away from the test room.

    2026-08-05 — Visual-loss and physical-station semantics separated¶

    Evidence level: recorded by commit eecf202, 126 passing tests, calibrated zone configuration, and the 2026-08-05 journal.

    Stale CSRT predictions were limited to one second without detector confirmation, and explicit LOST observations were introduced. Station occupancy no longer ends because the FTS moves inside a station or becomes temporarily invisible. A departure requires sustained detected movement outside the station envelope; one noisy outside point followed by visual loss is insufficient. The CHRG service polygon was corrected for the fixed camera geometry.

    2026-08-06 — OSF operational digital twin integrated¶

    Evidence level: recorded by commit 7e425f9, browser checks, 126 passing tests, and the 2026-08-06 journal.

    An 800×600 OSF operational view was added beside the calibrated Tracking map. It uses authorized ORBIS logos, station pictograms, intersections, and AGV graphics with recorded source revision. Camera-space FTS evidence is projected onto the operational route for Live and Replay, while the original Tracking view remains the engineering source for calibration inspection. Operational module state and future MQTT state remain conceptually separate from CV visual evidence.

    2026-08-10 to 2026-08-12 — Workpiece feasibility established¶

    Evidence level: recorded by commit 0ff826d, the WP-1 protocol, append-only annotations, and the observability report.

    A separate workpiece study was opened without changing the validated FTS pipeline. Red, blue, and white _1 recordings were assigned to development; the corresponding _2 recordings were sealed for later evaluation. A content-blind 36-frame audit was prepared and the dashboard was extended for native-resolution, multi-piece annotation with per-piece evidence.

    All 36 frames were reviewed. The final evidence contains 717 frame-level observations and represents all three colours, on-FTS transport, and station/handover contexts. WP-1 therefore passed its human-observability gate. This does not establish detector or tracking accuracy: the sample is dominated by static background pieces and contains no explicit negative frames.

    The study advanced to WP-2. Fourteen 12-second candidate windows were proposed from the three _1 recordings with checksum-verified 15 FPS review clips and one-second progression sheets. The proposal covers all colours and hypothesised transport, station, handover, occlusion, empty-FTS, and background-negative conditions. These hypotheses still require human acceptance before the sequence set is frozen. Detector comparison remains deferred and _2 sources remain sealed.

    2026-08-14 — Workpiece temporal windows human-reviewed and frozen¶

    Evidence level: recorded by the checksum-bound WP-2 review configuration and the sequence-review report.

    Human review accepted all 14 development windows without changing their 12-second boundaries. The clips provide visible transport, station, handover, occlusion, and empty-FTS evidence across red, blue, and white workpieces. The review corrected the preliminary proposal: all three supposed background negatives contain active DPS workpiece handling. The windows are frozen for 5 FPS annotation, but separate verified background negatives are still required. No _2 source was opened.

    The checksum-bound 5 FPS queue was then generated from those frozen _1 windows: 840 native-resolution frames, with exactly 60 half-open samples per window. A dedicated append-only browser workflow was validated for drawing, moving, resizing, explicit copy-forward review, ambiguity rationale, and reload persistence. Human frame annotation remains pending, and the missing verified background-negative evidence continues to block WP-2 completion.

    2026-08-20 — WP-2 development-frame annotation completed¶

    Evidence level: recorded by the evidence-bound temporal summary, 840 latest frame decisions, the append-only decision log, and the temporal annotation report.

    The first human pass completed all 840 prepared frames across the 14 frozen development sequences. The authoritative projection contains 16,835 visible frame-level instances and 281 temporary sequence-scoped identities. The append-only history contains 1,150 decisions, retaining 310 superseded rows as correction evidence. Every prepared frame has a decision and none remains pending.

    This closes the development-frame annotation completeness sub-gate only. Every prepared frame contains at least one visible workpiece, so the required background-negative evidence is still absent. The held-out protocol and its future second review also remain pending; _2 sources remain sealed and detector comparison has not started.

    Later the same day, 30 fixed 640×540 spatial proposals were generated from the existing checksum-bound _1 JPEGs and authoritative boxes, without decoding source video. Human review completed all 30; every authoritative decision is verified_negative, with ten crops per development session and six per configured region. The spatial negative screening gate passed. The evidence is limited to crops from nine source frames and cannot be reported as full-frame absence. The development ground-truth sub-gate is complete; _2 remains sealed until the held-out annotation protocol and detector candidates are locked.

    The held-out protocol was then frozen without reading _2 media. It defines three duration-normalized 12-second windows per sealed source, producing 540 future 5 FPS frames, and fixes annotation, independent second review, prediction-first blinding, metrics, matching, and acceptance rules. This closes WP-2 but does not authorize sealed release. Detector and tracker candidates must be developed and locked on _1 evidence first, then a separate explicit release record is required. WP-3 became active.

    2026-08-21 to 2026-08-22 — WP-3 detector comparison completed¶

    Evidence level: recorded by locked configurations, training/checkpoint hashes, raw validation predictions, class-aware metrics, and visual error-review artifacts.

    A static HSV/shape baseline and a supervised YOLO11n candidate were compared on the same sequence-grouped _1 evidence. The classical method failed with macro F1 0.0819. YOLO11n training ran on CPU because no CUDA-capable NVIDIA device was available. An interruption during epoch 16 was recorded and resumed from the preserved checkpoint without changing data or parameters. Patience-based early stopping ended training after epoch 37; the best checkpoint was epoch 25.

    The frozen custom evaluator selected confidence 0.20 and measured macro F1 0.9205, overall recall 0.9167, AP50 0.9411, and per-colour recall above 0.89. All 15 validation spatial-negative crops remained prediction-free. Review of the ten largest repeated unmatched-prediction clusters found visible inventory and localization disagreement rather than station-hardware confusers. However, station-context recall was only 78/144 and remains a documented tracking risk.

    The supervised detector was locked for WP-4 development. This is development-selection evidence because validation also informed early stopping, checkpoint selection, and threshold selection. No _2 source was opened; sealed release remains blocked until a tracker candidate and combined release record are locked.

    2026-08-22 — WP-4 temporary tracker selected and locked¶

    Evidence level: recorded by the pre-output tracker protocol, two hashed raw prediction streams, multi-identity metrics, and the tracker candidate lock.

    Greedy detector-corrected association was compared with class-aware global motion assignment on 360 prepared _1 frames containing 7,255 visible identity instances. Both passed the existing development gate. The global candidate was selected with 0.9218 temporal coverage, minimum per-colour coverage 0.9022, seven ID switches, zero simultaneous identity swaps, and 30 fragments.

    The result also exposed a major limitation: static inventory dominates the aggregate, while handover, on-FTS, and station coverage are only 0.3084, 0.3000, and 0.5556. The tracker is locked according to the predeclared rule, but robust moving-workpiece tracking is not claimed. _2 remains sealed; the combined release record and explicit operator confirmation have not been provided.

    2026-08-22 — Held-out release record prepared, not authorized¶

    Evidence level: checksum-bound metadata and regression-tested access guards; no sealed media access.

    The combined release record was prepared only after the detector and tracker locks existed. It binds both locks, the original held-out protocol, the frozen acceptance rules, 540-frame sampling plan, raw prediction schemas, and the rule that prediction files must be hashed before annotation begins.

    The record remains blocked. No first-pass or independent second reviewer is yet assigned, explicit operator authorization has not been recorded, both candidate permission fields remain false, and no _2 source was opened.

    2026-08-22 — Held-out release authorized and predictions sealed¶

    Evidence level: authorized release record, preserved interruption record, 540-frame manifest, two hashed raw prediction streams, execution seal, and blinded-service regression tests.

    Daniel Wonkam explicitly authorized the frozen one-time procedure and ORIEL was assigned as the distinct independent reviewer. The initial attempt stopped before frame extraction when OpenCV reported 30.000125 FPS for metadata rounded to 30.0 FPS. The label-free interruption was preserved. A narrow 0.01 FPS codec metadata tolerance was tested; frame indices and all analytical settings stayed unchanged.

    The successful run extracted exactly 540 images from the nine predeclared windows, then generated and hashed one detector row and one tracker row per frame. No human labels existed and no pixels were displayed during prediction preparation. The prediction files are now immutable. A separate first-pass workspace exposes only checksum-bound images and Daniel's own labels; detector and tracker outputs are never serialized to annotation clients. First-pass annotation and ORIEL's independent review remain pending.
