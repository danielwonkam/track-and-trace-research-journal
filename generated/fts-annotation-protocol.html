    FTS ground-truth annotation protocol¶

    Dataset pilot: fts-pilot-v0.1
    Object class: fts
    Annotation geometry: one axis-aligned bounding box per visible FTS
    Storage format: Ultralytics YOLO detection labels plus a CSV audit manifest
    Protocol status: fts-ground-truth-v1 frozen; 66 positives and 12 negatives verified

    1. Purpose¶

    This protocol defines how the fischertechnik transport system (FTS) is sampled, annotated, reviewed, and split for detector evaluation. Its purpose is to make labels consistent enough to support a scientific comparison. It does not assume that the current YOLOE + CSRT baseline is correct.

    The first 48-frame pilot validates the instructions and exposes ambiguous cases. It is too small to support a final accuracy claim or detector selection.

    2. Annotation target¶

    Annotate the complete mobile FTS carrier as class fts (class_id = 0). The workpiece colour is incidental and must not create a separate class. Do not annotate fixed stations, chargers, rails, trays, workpieces, or other machinery as the FTS.

    Include¶

    • the visible mobile carrier body;
    • attached structural parts that move rigidly with the carrier; and
    • the carried tray only when it is structurally part of the carrier silhouette.

    Exclude¶

    • the coloured workpiece when it projects beyond the carrier body;
    • shadows, reflections, motion trails, and background objects;
    • fixed station structures, even when their shape resembles the FTS; and
    • guessed regions when no part of the FTS is visible.

    3. Bounding-box rule¶

    Draw the smallest axis-aligned rectangle enclosing all visible FTS pixels. Do not infer the full hidden size through a station or occluder. A box should be tight without cutting visible parts; a small margin of at most two pixels is acceptable when the boundary is anti-aliased or blurred.

    When motion blur is present, include the solid visible object but exclude faint motion trails. When the FTS touches an image boundary, clip the box to the image.

    4. Visibility decision¶

    Assign exactly one visibility value in the manifest:

    Value Rule
    clear At least 80% of the carrier is visible and its boundary is identifiable.
    partial Between 30% and 80% is visible, or a station hides part of the carrier.
    minimal Less than 30% is visible but the FTS identity and a defensible visible-region box remain clear.
    absent No FTS pixels are visible. The YOLO label file must exist and be empty.
    ambiguous The reviewer cannot distinguish the FTS from the scene confidently. Do not use the frame for model evaluation until resolved.

    For minimal, record a box only when the visible pixels are confidently the FTS. Otherwise use ambiguous rather than inventing a box.

    5. Difficulty tags¶

    Assign one or more semicolon-separated tags after inspecting the image:

    • clear_view;
    • motion_blur;
    • partial_occlusion;
    • station_overlap;
    • turn_or_unusual_pose;
    • difficult_lighting;
    • image_edge;
    • small_scale;
    • station_only_negative;
    • empty_scene_negative; or
    • other:<short explanation>.

    Sampling timestamps do not prove a difficulty category. Tags must be assigned by visual review, not automatically inferred from time or the baseline prediction.

    6. Positive, negative, and rejected frames¶

    • A positive frame has one defensible FTS box and a non-empty YOLO label.
    • A negative frame has visibility absent and an intentionally empty YOLO label file. Fixed stations should be represented among the negatives because they caused the dominant baseline failure.
    • An ambiguous frame is retained for discussion but excluded from training and evaluation until resolved.
    • A technically invalid frame (decode error, corruption, wrong source, or severe unusable blur) receives review status rejected with a reason.

    An absent label file means not annotated yet. It must never be interpreted as a negative example. An empty existing label file means verified negative.

    7. YOLO label format¶

    Each positive image has a text file with one row:

    0 x_center_normalized y_center_normalized width_normalized height_normalized

    All four coordinates must be in [0, 1]. Coordinates describe the reviewed pixel box, normalized by the original image width and height. The current videos contain one FTS; a frame with more than one apparent carrier must be marked ambiguous and discussed before use.

    8. Pilot sampling and split¶

    The deterministic sampler extracts eight evenly distributed timestamps from each of the six recordings, for 48 candidate frames. Even spacing provides coverage across each route but does not guarantee every required visual condition. After the contact sheets are reviewed, additional targeted frames must be added for missing conditions—especially fixed-station negatives, occlusion, motion blur, turns, and difficult lighting.

    The pilot uses a source-video split:

    Split Source videos Purpose
    train od_red_1, od_blue_1, od_white_1 Develop annotation and detector settings
    val od_red_2 Select settings without using test evidence
    test od_blue_2, od_white_2 Final held-out pilot check

    No frame from a validation or test video may be copied into training. If the split changes, create a new dataset version; do not silently edit the manifest. The final dataset must document the limitation that only six source recordings are available and report results by source video.

    9. Annotation workflow¶

    1. Run the dashboard and open FTS annotation in the left navigation.
    2. Enter the annotator’s name or initials once.
    3. For each image, drag one rectangle around the FTS or choose No FTS.
    4. Choose Unsure instead of guessing when the FTS cannot be identified.
    5. Record visibility, optional difficulty tags, and a note only when useful.
    6. Select Save & show next image. The interface writes the YOLO label, append-only decision, and manifest status automatically.
    7. Mark an item annotated only after checking box tightness and class identity.
    8. Finish every first-pass decision in the project before starting second review.
    9. A second review is mandatory for every validation and test item.
    10. Mark validation/test items verified only after that review.
    11. Resolve disagreements from the image itself, not from detector predictions.

    Validation/test second review¶

    After the complete project first pass, select Start validation/test second review. For fts-pilot-v0.1, the queue contains only the 8 validation and 16 test frames. Recheck the saved answer and any cyan box, identify the reviewer, and choose exactly one action:

    • Approve saved label when class, visible extent, and metadata are correct;
    • Save corrected answer after changing an incorrect class/visibility answer or redrawing incorrect geometry; or
    • Flag as unsure when the evidence cannot support approval or correction.

    Second reviews are append-only and separate from first-pass decisions. A correction replaces the authoritative YOLO label: a corrected positive writes the reviewed box, a corrected negative writes an empty label, and an ambiguous or rejected correction removes the label. The record retains both the first annotator and reviewer. Approval never silently changes the first-pass answer. A flagged frame is not verified and must be resolved before evaluation.

    The original JPEG is never painted or modified. The visible cyan rectangle is a browser overlay; only its pixel coordinates are saved.

    The current detector output may be displayed as a separate diagnostic overlay, but it must not be accepted as ground truth without manual placement and review.

    AI-assisted proposals¶

    An AI-assisted box is an unverified proposal, not an annotation. The interface displays proposals in orange and excludes them from completion counts, YOLO labels, and evaluation. A human reviewer must choose one action:

    • Accept proposal: confirm the suggested class and box unchanged;
    • Adjust box: replace or redraw the suggested geometry;
    • Reject proposal: remove it and provide a new answer; or
    • Unsure: retain the frame for discussion instead of guessing.

    After the reviewer explicitly saves, the decision becomes human-verified ground truth and records the proposal method plus whether it was accepted, adjusted, or rejected. The first five proposals form a calibration pilot. Their human review must be inspected before AI proposals are created for the remaining frames.

    Targeted negative-candidate review¶

    The separate fts-negative-candidates-v0.1 project contains two pending frames from each source recording. Candidate timestamps preferentially come from the latest manually reviewed baseline detector errors, with recording-endpoint fallbacks where a source has fewer than two distinct error timestamps. This selection targets station confusers; it does not establish FTS absence.

    Inspect the complete image in the ordinary first-pass workflow:

    • choose No FTS only when no FTS pixels are visible anywhere in the frame;
    • draw a normal FTS box when the detector was wrong but the FTS remains visible;
    • choose Unsure rather than manufacturing either a positive or negative;
    • assign station_only_negative or empty_scene_negative only after visual verification; and
    • second-review every validation and test decision before dataset freeze.

    Extraction creates image files and pending manifest rows, but deliberately creates no label files. A human No FTS decision is the only operation that may create an empty YOLO label.

    Declared-empty source verification¶

    The fts-verified-negatives-v0.1 project samples two new close-plan recordings:

    • cluttered empty operational view: 6 training candidates; and
    • clean empty operational view: 6 held-out test candidates.

    The complete source recordings remain split-disjoint. Filenames and recording intent are selection evidence, not labels. Every sampled image requires the same whole-frame decision as a targeted candidate. A human No FTS save creates the empty label; the six test decisions then require second review before they can enter evaluation.

    The wide-plan empty recording changes camera geometry and is reserved as an out-of-distribution stress source. It must not be mixed into the calibrated core dataset. New low-light route recordings and the cluttered CHRG recording are retained as future robustness evidence; they do not replace the missing core negative verification.

    Declared-empty result and frozen version¶

    All 12 close-plan candidates were manually verified as No FTS. The six test decisions passed the mandatory second review. The combined fts-ground-truth-v1 freeze contains 78 frames: 66 positives and 12 negatives, split into 42 train, 10 validation, and 26 test frames. The freezer verified image checksums, class-0/empty-label consistency, held-out review completion, duplicate absence, and source-video isolation. Its deterministic freeze SHA-256 is 31b68230c3dfea649ee14dae591f4a24485f68f8a787f2f13c4f4df73c95100b.

    The first annotator also performed every held-out second review. These checks are valid documented quality control under this protocol, but they must not be described as independent inter-annotator verification.

    10. Quality checks¶

    Before a dataset version is frozen, verify that:

    • every manifest row points to the expected source video, timestamp, and frame;
    • image checksums and dimensions are recorded;
    • every clear, partial, or minimal row has exactly one valid class-0 box;
    • every absent row has an existing empty label file;
    • no pending, ambiguous, or rejected row enters evaluation;
    • every validation and test row has reviewer name and review status verified;
    • each video contributes useful positive and difficult or negative evidence;
    • train, validation, and test source videos remain disjoint; and
    • a contact-sheet spot check shows no systematic loose boxes or station labels.

    11. Pilot acceptance decision¶

    After all 48 candidates are inspected, record:

    • the number of positive, negative, ambiguous, and rejected frames per video;
    • the represented difficulty conditions and missing conditions;
    • annotation-rule disagreements and their resolution;
    • whether the split remains suitable; and
    • the exact targeted frames needed before freezing fts-ground-truth-v1.

    Only then should full annotation continue. Detector comparison begins after the versioned dataset passes the Milestone 2 acceptance gate.
