    Scientific decision register¶

    Status values: active, superseded, rejected, or planned.

    D-001 — Observe rather than control the shopfloor¶

    • Date: 2026-07-13 or earlier; present in the initial project definition
    • Status: active
    • Problem: define the system boundary for a safe thesis demonstrator.
    • Decision: use cameras to observe and reconstruct Track & Trace information; never send control commands to the shopfloor.
    • Rationale: this isolates perception and interpretation, avoids operational safety risks, and permits comparison with existing system records.
    • Evidence: project instructions, README, and quality criteria.
    • Consequence: MQTT/OPC-UA may be used as evaluation reference, not as an input required for AI reconstruction.

    D-002 — Use a layered perception pipeline¶

    • Date: 2026-07-13
    • Status: active
    • Problem: keep computer-vision and Track & Trace logic testable.
    • Decision: separate capture, detection, tracking, zone mapping, interpretation, storage, evaluation, and dashboard responsibilities.
    • Alternatives: one monolithic script or dashboard-owned processing.
    • Rationale: independent layers permit isolated tests, method replacement, and clearer experimental attribution.
    • Evidence: initial commit, package layout, README, and tests.

    D-003 — Use hybrid FTS detection and tracking for the first prototype¶

    • Date: 2026-07-20
    • Status: active as baseline; not approved for final live transfer
    • Problem: detect an FTS without first producing a labelled training set and maintain positions between expensive detections on CPU.
    • Decision: initialize with a single-reference YOLOE visual prompt and track between periodic detections with OpenCV CSRT.
    • Alternatives: train a one-class detector immediately; use ByteTrack or BoT-SORT from the beginning; use only classical image processing.
    • Rationale: visual prompting enabled rapid zero-training prototyping, while CSRT reduced repeated inference cost and worked with one object.
    • Evidence: commit 3e47e72, hybrid scripts, and baseline configuration.
    • Limitation discovered: the detector often selected a station, after which CSRT produced a continuous but semantically wrong trajectory.

    D-004 — Replace Streamlit with FastAPI and a browser-native frontend¶

    • Date: 2026-07-21 to 2026-07-27
    • Status: active
    • Problem: the planned Streamlit rerun model was unsuitable for direct, low-latency video and independently updating live state.
    • Decision: use FastAPI, plain HTML/CSS/JavaScript, WebSocket state/events, and MJPEG annotated video.
    • Alternatives: continue Streamlit; use a React build; use a desktop GUI.
    • Rationale: the selected stack supports independent streaming channels, explicit API boundaries, a lightweight deployment, and precise frontend control without adding a frontend build system.
    • Evidence: dashboard implementation, README, dashboard tests, and current working application.

    D-005 — Use latest-frame transport for live operation¶

    • Date: 2026-07-21 to 2026-07-27
    • Status: active
    • Problem: queued or disk-polled frames caused visible latency.
    • Decision: capture continuously, keep only the newest frame, drop stale frames, and publish the latest encoded preview through shared memory.
    • Alternatives: process every frame in order; poll image files from disk.
    • Rationale: for live observation, freshness is more important than processing every frame; stale frames make the dashboard temporally misleading.
    • Evidence: live capture and shared-preview modules plus live tests.

    D-006 — Preserve review history as append-only JSONL¶

    • Date: 2026-07-27 to 2026-07-28
    • Status: active
    • Problem: allow human corrections without deleting experimental evidence.
    • Decision: append every verdict and treat the latest row per candidate as authoritative.
    • Alternatives: overwrite one mutable record; edit baseline outputs directly.
    • Rationale: append-only history supports traceability, correction, and reproducible summary generation.
    • Evidence: failure_review.jsonl, review service, summary generator, and regression test.

    D-007 — Evaluate the unchanged method before tuning¶

    • Date: 2026-07-27
    • Status: active methodological rule
    • Problem: ad hoc tuning can hide failure modes and produce an irreproducible method.
    • Decision: run one recorded configuration on all six videos and review its failures before modifying thresholds or references.
    • Rationale: a fixed baseline allows later methods to be compared against the same evidence.
    • Evidence: FTS roadmap, baseline config, metrics, and review report.

    D-008 — Do not use confidence thresholding as the main correction¶

    • Date: 2026-07-28
    • Status: active
    • Problem: determine whether a higher YOLOE confidence threshold could reject station false locks.
    • Decision: do not tune only the threshold.
    • Rationale: reviewed station false locks had a higher mean confidence (0.1354) than correct locks (0.1205); confidence therefore did not separate the classes in this baseline.
    • Evidence: manual review summary.
    • Next comparison: multi-view visual prompting versus a dedicated one-class detector on held-out videos.

    D-009 — Focus exclusively on the FTS before expanding analytics¶

    • Date: 2026-07-28
    • Status: active
    • Problem: limit thesis scope and prevent later outputs from depending on an unreliable carrier trajectory.
    • Decision: complete FTS detection, tracking, calibration, and live validation before extending workpiece tracking, custody, event reconstruction, or detailed dashboard statistics.
    • Alternatives: develop all object classes and analytics in parallel.
    • Rationale: downstream assignments and statistics are not scientifically meaningful if the FTS itself is frequently misidentified.
    • Evidence: supervisor meeting of 2026-07-28 and FTS roadmap.

    D-010 — Seal test evidence before detector development¶

    • Date: 2026-07-31
    • Status: active methodological rule
    • Problem: repeated test inspection would turn the held-out set into tuning evidence and make the final comparison optimistic.
    • Decision: permit prompt, threshold, constraint, architecture, and checkpoint selection only on train and validation sources. Keep all 26 test frames inaccessible to development runners until both detector candidates and their validation results are locked.
    • Alternatives: inspect test metrics after every change; tune all available frames; report Ultralytics defaults without a local evaluation contract.
    • Rationale: a small dataset is especially vulnerable to test leakage. A machine-enforced release gate makes the final comparison reproducible and falsifiable.
    • Evidence: configs/experiments/fts_detector_evaluation_v1.json, docs/research/FTS_DETECTOR_EVALUATION_V1.md, and evaluator regression tests.

    D-011 — Isolate workpiece feasibility from the validated FTS pipeline¶

    • Date: 2026-08-10
    • Status: active experimental boundary
    • Problem: investigate the supervisor-proposed workpiece capability without destabilising or contaminating the selected FTS detector, tracker, Replay, Live behavior, or station-event evidence.
    • Decision: use branch experiment/workpiece-feasibility and the separate workpiece_study/ area. Read existing videos as immutable inputs; require observability, detection, tracking, and custody gates before integration.
    • Alternatives: modify the current live pipeline immediately; create an unrelated repository; acquire arbitrary new data before testing existing data.
    • Rationale: separation preserves the validated carrier evidence while allowing a falsifiable feasibility study. Existing recordings should reveal concrete visibility and coverage gaps before new acquisition is designed.
    • Scope relation: D-009 remains the application-integration boundary. This decision permits isolated feasibility preparation after FTS detector/tracker selection; it does not certify workpieces or merge them into operations.
    • Evidence: workpiece_study/PROTOCOL.md, workpiece_study/ROADMAP.md, and workpiece_study/STARTUP_RECORD.md.

    D-012 — Permit only explicit reviewed-box propagation within one recording¶

    • Date: 2026-08-11
    • Status: active annotation rule
    • Problem: static pieces make repeated manual boxes expensive, but the 36 WP-1 frames are widely separated samples rather than consecutive video frames.
    • Decision: offer an optional copy from the closest earlier reviewed frame in the same recording. Display copied boxes as unverified, require explicit current-frame review before save, and record the source frame as provenance.
    • Rejected alternative: silently copy the first layout to every frame or propagate boxes across recordings.
    • Rationale: bounded propagation reduces repetitive work without treating a previous observation as current ground truth or hiding temporal changes.
    • Evidence: workpiece copy-source API safeguards, browser validation, and tests/test_workpiece_audit.py.

    D-013 — Advance workpiece feasibility to temporal ground truth¶

    • Date: 2026-08-12
    • Status: active experimental decision
    • Problem: decide whether the completed WP-1 audit supports detector work, requires new acquisition, or requires stronger temporal evidence first.
    • Decision: close WP-1 as passed and begin WP-2 by freezing targeted 8–12 second sequences from the _1 development recordings. Prioritize on-FTS, station/handover, occlusion, and explicit negative conditions. Keep _2 sources sealed and defer detector comparison until the WP-2 protocol and development labels are complete.
    • Rejected alternatives: train immediately from the sparse sampled frames; open _2 sources for sequence selection; acquire new video before checking whether the existing development recordings contain the required cases.
    • Rationale: all colours and required contexts are human-observable, so immediate acquisition is not justified. However, isolated frames cannot establish temporal continuity, and the WP-1 sample contains no negatives and is dominated by static background inventory.
    • Evidence: docs/research/WORKPIECE_WP1_OBSERVABILITY.md and the completed append-only WP-1 decisions.

    D-014 — Freeze reviewed workpiece windows but reject negative hypotheses¶

    • Date: 2026-08-14
    • Status: active experimental decision
    • Problem: decide whether the 14 proposed _1 windows are suitable for temporal annotation and whether their coarse evidence hypotheses are valid.
    • Decision: freeze all 14 original 12-second boundaries for 5 FPS annotation. Replace proposal hypotheses with the human-reviewed observations in workpiece_study/configs/temporal_candidate_review_v0.1.json.
    • Rejected alternative: treat the proposal tags as truth or discard useful station windows merely because an expected tag was incorrect.
    • Rationale: every window contains visible workpiece evidence, but the three proposed background negatives contain active DPS handling. Preserving the original proposal and recording a separate review makes the correction auditable without rewriting history.
    • Consequence: frame annotation may begin, but WP-2 cannot close until true background negatives are separately selected and verified. _2 sources remain sealed.
    • Evidence: docs/research/WORKPIECE_WP2_SEQUENCE_REVIEW.md and the checksum-bound review configuration.

    D-015 — Accept WP-2 annotation completeness without closing WP-2¶

    • Date: 2026-08-20
    • Status: active experimental decision
    • Problem: decide whether completion of all prepared temporal-frame labels is sufficient to close WP-2 and begin detector comparison.
    • Decision: accept the development-frame annotation completeness sub-gate: 840/840 frames have authoritative decisions. Keep WP-2 open until separate background-negative evidence is selected and verified and the held-out protocol is locked.
    • Rejected alternative: treat zero pending labels as completion of the whole WP-2 milestone or reinterpret the three disproved background proposals as negatives.
    • Rationale: completeness and evidence coverage are distinct. The completed queue contains 16,835 visible instances but no absent frame, so it cannot support a defensible false-positive assessment on true background negatives.
    • Consequence: preserve the current append-only labels, keep _2 sealed, and acquire the missing negative evidence before detector comparison.
    • Evidence: docs/research/WORKPIECE_WP2_TEMPORAL_ANNOTATION.md and the evidence-bound temporal summary.

    D-016 — Accept verified spatial negatives without claiming empty frames¶

    • Date: 2026-08-20
    • Status: active experimental decision
    • Problem: no completed temporal frame is workpiece-free, while WP-2 still requires explicit negative evidence and _2 must remain sealed.
    • Decision: accept the 30/30 human-verified 640×540 development crops as spatial negative evidence for later crop/tile false-positive analysis. Close the development ground-truth sub-gate, but explicitly keep full_frame_absence_verified = false and keep WP-2 open until the held-out annotation protocol is locked.
    • Rejected alternative: auto-label box-free proposals, reinterpret a crop as proof that its full frame is empty, open _2, or silently broaden the source policy to unrelated recordings.
    • Rationale: direct human review provides explicit negative labels within the displayed regions. All 30 candidates passed the predeclared coverage gate, while the scope statement preserves the distinction between local and whole-frame evidence.
    • Consequence: crop/tile detector experiments may use this evidence after protocol locking. Whole-frame no-object performance remains unmeasured; the 30 crops come from nine source frames and are not independent observations.
    • Evidence: docs/research/WORKPIECE_WP2_SPATIAL_NEGATIVES.md, the generated manifest, and the append-only crop decision log.

    D-017 — Lock held-out procedure and close WP-2 without opening _2¶

    • Date: 2026-08-20
    • Status: active experimental decision
    • Problem: freeze a defensible one-time held-out evaluation before pixels can influence sampling, annotation, candidate selection, or thresholds, while avoiding a roadmap cycle between WP-2 labels and WP-3/WP-4 candidate locks.
    • Decision: lock three duration-normalized 12-second windows per _2 source, 5 FPS sampling, 540 future frames, the annotation schema, mandatory independent second review, prediction-first blinding, matching, metrics, and acceptance gates. Close WP-2 now, but do not authorize _2 release until detector and tracker candidates are both frozen and a separate release record receives explicit authorization.
    • Rejected alternative: inspect _2 to choose favorable windows, mirror development timestamps without a route correspondence, release after only a detector lock, or expose labels before raw predictions are sealed.
    • Rationale: duration-normalized metadata-only selection is reproducible and pixel-independent. Delaying release until both candidate families are locked prevents held-out temporal labels from influencing tracker development.
    • Consequence: WP-3 may begin using _1 evidence only. The future _2 result remains an internal source-held-out check, requires a different second reviewer, and cannot trigger tuning; failure requires new development work and prospective test data.
    • Evidence: workpiece_study/configs/held_out_protocol_v0.1.json and docs/research/WORKPIECE_WP2_HELD_OUT_PROTOCOL_LOCK.md.

    D-018 — Select and lock the supervised workpiece detector¶

    • Date: 2026-08-22
    • Status: active experimental decision
    • Problem: decide whether either frozen WP-3 detector provides sufficient development evidence to begin temporary tracking without opening _2.
    • Decision: reject static-hsv-shape-v0.1 and lock supervised-yolo11n-workpiece-v0.1 for WP-4 development. Freeze checkpoint SHA-256 300f852bc6af002cc4f5897c3897aeb8391772d454b4b595c086a78b8b1c38ae, 960-pixel full-frame CPU inference, confidence 0.20, NMS IoU 0.70, and the red/blue/white class map.
    • Rationale: the supervised candidate achieved macro F1 0.9205 and recall 0.9031/0.9621/0.8917 for red/blue/white, passing the numerical gate. Review of the ten largest repeated unmatched-prediction clusters found visible workpieces/localization disagreement rather than station hardware confusers.
    • Known weakness: station-context recall is 78/144 (0.5417), with misses concentrated in red and blue manipulation/occlusion evidence. WP-4 must not hide this limitation behind aggregate accuracy.
    • Rejected alternative: promote the faster classical baseline, tune the supervised model after seeing validation errors, or open _2 before tracker lock.
    • Consequence: WP-4 may begin on _1. _2 release remains unauthorized until the tracker candidate and combined release record are locked.
    • Evidence: docs/research/WORKPIECE_WP3_DETECTOR_COMPARISON.md and workpiece_study/configs/detector_candidate_lock_v0.1.json.

    D-019 — Lock global motion association while rejecting a broad robustness claim¶

    • Date: 2026-08-22
    • Status: active experimental decision
    • Problem: select a temporary tracker under the frozen WP-4 gate without allowing static inventory to hide material-flow failures.
    • Decision: lock global-motion-lap-association-v0.1. It uses class-aware Jonker–Volgenant assignment, constant-velocity prediction for at most 0.4 seconds, and sequence-scoped identities. Keep _2 sealed pending the separate combined release record and explicit operator confirmation.
    • Rationale: both candidates passed. The selected tracker had higher minimum per-colour coverage (0.9022 versus 0.8917), zero identity swaps, fewer ID switches (7 versus 10), and fewer fragments (30 versus 38).
    • Limitation: aggregate coverage 0.9218 is dominated by static inventory. Coverage is 0.3084 for handover, 0.3000 on-FTS, and 0.5556 at stations, with a 6.2-second longest miss. Robust moving-workpiece tracking is not claimed.
    • Rejected alternative: select the lower-latency greedy tracker contrary to the frozen ranking, tune association after validation results, or interpret the aggregate gate as production readiness.
    • Evidence: docs/research/WORKPIECE_WP4_TRACKER_COMPARISON.md and workpiece_study/configs/tracker_candidate_lock_v0.1.json.

    D-020 — Prepare the combined held-out release record without authorizing access¶

    • Date: 2026-08-22
    • Status: active methodological checkpoint
    • Problem: bind the final detector, tracker, sampling, gates, and output schemas before _2 access without treating preparation as authorization.
    • Decision: create workpiece-held-out-release-v0.1 in prepared_pending_explicit_authorization state. Bind the held-out protocol, both candidate locks, frozen acceptance rules, and prediction-before-label ordering. Keep every sealed-access flag and permission false.
    • Rationale: a reviewable draft closes the technical reproducibility gap while preserving a separate, explicit human decision at the irreversible release boundary.
    • Remaining blockers: assign different first-pass and second reviewers and obtain explicit operator confirmation for the one-time _2 release.
    • Rejected alternative: infer authorization from the request to prepare the record, mutate candidate locks, or inspect sealed media while checking the release prerequisites.
    • Evidence: workpiece_study/configs/held_out_release_v0.1.json and docs/research/WORKPIECE_HELD_OUT_RELEASE_PREPARATION.md.

    D-021 — Authorize and seal the one-time held-out prediction streams¶

    • Date: 2026-08-22
    • Status: active irreversible evaluation boundary
    • Decision: assign Daniel Wonkam as first-pass reviewer and ORIEL as the distinct independent reviewer; record explicit operator authorization; then extract only the nine frozen _2 windows and generate detector and tracker predictions before exposing images for annotation.
    • Interruption: the first attempt stopped before extraction because the codec reported 30.000125 FPS instead of metadata-rounded 30.0 FPS. Preserve that label-free failure and allow a 0.01 FPS metadata tolerance without changing any frozen frame index or analytical parameter.
    • Result: 540 frames, 540 detector rows, and 540 tracker rows were produced. Detector SHA-256 is 5c4404e22a11dd5ac7a0faab4c458096e7a2c1465fdf1bd8396e0a613c26eab0; tracker SHA-256 is caf711a7212eb2d2165e676034d299eff51a42420d57fb5e36852fa328b7b684.
    • Constraint: predictions cannot be regenerated after this boundary and cannot be exposed to either annotator. No held-out result may tune the model, threshold, sampling, crop/tile strategy, tracker, or acceptance gates.
    • Evidence: experiments/runs/20260822_workpiece_held_out_v0.1/execution_seal.json and docs/research/WORKPIECE_HELD_OUT_RELEASE_PREPARATION.md.

    D-022 — Report the held-out result as provisional without independent review¶

    • Date: 2026-09-03
    • Status: active protocol deviation; final gate blocked
    • Problem: all 540 first-pass annotations were complete, but the assigned independent reviewer was unavailable to repeat the review.
    • Decision: record the deviation before viewing results, then evaluate the unchanged sealed predictions once against the first pass. Label every output as provisional and prevent numerical checks from becoming a final gate pass.
    • Rationale: preserving the pre-label prediction hashes still provides useful internal evidence, while an explicit limitation is more defensible than claiming independence that did not occur or discarding the completed annotation work.
    • Result: the numerical checks did not all pass. Detector macro F1 was 0.7976; red recall was 0.6667. Tracker coverage was 0.6703/0.8492/0.7222 for red/blue/white, with zero simultaneous identity swaps.
    • Constraint: do not tune against these held-out frames. If they become training data, obtain a new unseen source for later evaluation.
    • Evidence: workpiece_study/configs/held_out_single_reviewer_deviation_v0.1.json and docs/research/WORKPIECE_HELD_OUT_PROVISIONAL_EVALUATION.md.

    D-023 — Keep prospective quality review separate from annotation and scoring¶

    • Date: 2026-09-14
    • Status: targeted QA completed 2026-09-15; scoring governed separately by D-025
    • Problem: the completed composite first pass needs a quality check without overwriting its original labels or treating completion as independent verification.
    • Decision: freeze the complete first-pass history, both seals and composite membership; structurally validate all 360 frames; prepare same-reviewer visual QA for the 60-frame replacement sequence. Preload human boxes but require explicit confirmation and reasoned corrections in a different append-only store.
    • Rationale: review of transport/handover/station transitions should not force every frame into a dual-carrier state or use detector errors as selection hints.
    • Limitations: declared after first pass, before scoring. Not independent review, not full visual QA of the other five windows, not scoring release. The earlier held-out single-reviewer deviation is not automatically transferred here.
    • Evidence: workpiece_study/configs/prospective_quality_review_v0.1.json, workpiece_study/configs/prospective_quality_review_v0.2.json, dashboard/workpiece_prospective_review.py, and the daily journals for 2026-09-14 and 2026-09-15. The final v0.2 state contains 60/60 confirmed frames, zero corrections and zero unresolved frames.

    D-024 — Recover stale QA with a new snapshot, not relaxed integrity checks¶

    • Date: 2026-09-14 (session date)
    • Status: active; v0.2 prepared, v0.1 preserved
    • Problem: an unchanged first-pass re-save at 16:57:23 UTC extended history from 525 to 526 entries. The v0.1 byte binding correctly rejected it, but the UI misleadingly left an empty canvas, loading progress and enabled controls.
    • Decision: retain the original history and v0.1 bundle; prepare a separately configured v0.2 from current history. Do not bypass checks or transfer approvals. Disable annotation actions until the selected image is valid; expose blocked state, a specific error and a retry that never changes evidence.
    • Evidence: the old history is a byte-exact prefix of the new one and the appended record has unchanged canonical annotation fields. All other v0.1 bindings match. New configuration: workpiece_study/configs/prospective_quality_review_v0.2.json.
    • Limitation: another first-pass save still requires an explicit new version. This change neither locks the first-pass editor nor authorizes scoring.

    D-025 — Evaluate the prospective composite under a declared single-reviewer deviation¶

    • Date: 2026-09-15
    • Status: active protocol deviation; numerical checks failed and final gate blocked
    • Problem: the 360-frame prospective first pass and targeted replacement QA were complete, but no independent reviewer was available for the next gate.
    • Decision: record Daniel Wonkam's explicit authorization before viewing results, freeze a one-time scoring release, then evaluate the unchanged sealed predictions. Keep the 300 evaluation-role frames separate from the 60 development-reserve frames and label all outputs provisional single-reviewer.
    • Bindings: the release fixes both execution seals and prediction hashes, both manifests, first-pass and QA histories, evaluation implementations, IoU 0.50, confidence 0.20, the 300/60 role split and existing numerical gates.
    • Result: on the evaluation role, detector macro F1 was 0.1193 and recall was 0.0417/0.1161/0.0580 for red/blue/white. Tracker temporal coverage was 0.0417/0.1223/0.0681, with five ID switches, zero simultaneous identity swaps and 15 fragments. Only the zero-swap numerical observation passed.
    • Development reserve: detector macro F1 was 0.2230 and tracker temporal coverage was 0.1429; these observations are reported separately and do not alter the evaluation-role decision.
    • Interpretation: the frozen candidate shows a large prospective transfer failure. The result is not a final gate pass or production certification: annotation quality lacks independent review, QA covered only the replacement sequence and station-event scoring remains unauthorized.
    • Constraint: do not tune on the evaluation-role frames. Any model, tracker, threshold or sampling change requires a new unseen prospective source before a later performance claim.
    • Evidence: workpiece_study/configs/prospective_single_reviewer_deviation_v0.1.json, workpiece_study/configs/prospective_single_reviewer_release_v0.1.json, and experiments/runs/20260915_workpiece_prospective_provisional_v0.1/PROVISIONAL_SINGLE_REVIEWER_REPORT.md.
